# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Game-style ground control station for an ArduPilot **QuadPlane**: C++17, Qt 6 Widgets, MAVLink v2 over UDP or serial (USB / telemetry radio), optional GStreamer H.264 video. See `README.md` for prerequisites, run flags, controls and settings.

## Commands

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo   # -DGCS_WITH_GSTREAMER=OFF to skip video
cmake --build build
ctest --test-dir build --output-on-failure      # all tests
ctest --test-dir build -R mission_transfer      # one test (geo, endurance, mission_builder, mission_transfer, command_sender, lift_rotors, health, orbit_trim, preflight, offline_map, transport, plan_library, ...)
./build/test_geo                                # or run a test binary directly
./build/mavlink_gcs_ui                          # listens on udp 127.0.0.1:14551
```

SITL (ArduPilot checkout at `~/ardupilot`):

```sh
tools/sitl.sh            # sim_vehicle.py quadplane at your (IP) location, else Israel; --no-geo skips the lookup
# same as: cd ~/ardupilot && Tools/autotest/sim_vehicle.py -v ArduPlane -f quadplane -l LAT,LON,ALT,HDG \
#          --out=udp:127.0.0.1:14551 --add-param-file=tools/sitl_extra.parm
```

There is no linter; the build uses `-Wall -Wextra -Wpedantic` (MSVC: `/W4 /permissive- /utf-8`) and should stay warning-free. New tests go in `tests/test_<name>.cpp` using the `CHECK` / `CHECK_NEAR` / `TEST_MAIN_RESULT()` macros from `tests/check.hpp` (no framework), and the name must be added to the `foreach` list in `CMakeLists.txt`.

## Portability (Linux, Windows, macOS)

The app ships on all three; `.github/workflows/build.yml` builds, tests and packages each push on ubuntu / windows (MSVC) / macos. Day-to-day work and SITL stay on Linux, so these rules are what keep the other two working. CI must pass on all three before a merge.

**Every PR gets a full build and test on Windows and macOS before it is called done** (not needed for each push while the work is in progress). That means the CI run for the PR's head commit is green on all three jobs (build, `ctest`, package; `gh pr checks <N> --watch`), and when a real Windows PC or Mac is reachable, the app is also built, tested and started there. Say in the PR which of the two happened.

- **OS calls only in shims.** Outside `src/link/*_transport.cpp` (and any future `platform/` file), nothing includes `<sys/*>`, `<unistd.h>`, `<arpa/*>`, `<netinet/*>`, `<poll.h>`, `<fcntl.h>`, `<termios.h>`, `<windows.h>` or `<winsock2.h>`. `ui` uses Qt APIs; `core` is pure standard C++ with no I/O.
- **No Linux-only APIs**, even in POSIX branches (`eventfd`, `epoll`, `inotify`, `/proc`, `prctl`, `udev`): macOS is POSIX, not Linux. `__linux__`-only extras (like `/dev/serial/by-id` names) need a fallback on the other branches.
- **Platform `#if`:** only `_WIN32` / `__APPLE__` / `__linux__` (or `Q_OS_*` in ui), only in shims, and every branch must compile. Code you can't compile here gets compiled by CI; push and watch it (`gh run watch`).
- **Paths:** only `QStandardPaths` / `QDir::filePath` / `QFile`. No hard-coded `/home`, `/tmp`, `~` or `/`-joined absolute paths, and no `fopen(std::string)`, which breaks on non-ASCII paths on Windows.
- **Fonts:** only the bundled `theme::kSansFamily` / `kMonoFamily` (DejaVu, `resources/fonts`, registered by `theme::loadFonts()`). Never name a font the OS may not have.
- **Standard C++ only.** It has to build on GCC, Apple Clang and MSVC. So: no `M_PI` (use `geo::kPi`), VLAs, `__attribute__`, `__builtin_*`, `ssize_t` or designated initializers. Get byte order from explicit shifts (as `pmtiles` / `mvt` do), never by casting buffers. Sources are UTF-8.
- **Links** go through `Transport`. A serial link must survive the port vanishing and coming back (USB unplugged, autopilot reboot).
- **Input:** every gesture has a touch path *and* a mouse/trackpad path (wheel, `QNativeGestureEvent` pinch on macOS). All typed input goes through `EntryPad`.
- **DPR:** cached pixmaps are created at `devicePixelRatioF()`. Paint-budget numbers below were measured at DPR 1; a Retina screen paints 4× the pixels, so state the DPR with any new measurement.
- **Packaging:** Windows is `WIN32_EXECUTABLE` + `resources/windows/*.rc` (icon); macOS is a bundle with `resources/macos/Info.plist.in` (`NSLocalNetworkUsageDescription` is required for UDP from the LAN on macOS 15+). `cmake --install` runs windeployqt / macdeployqt (`qt_generate_deploy_app_script`, Qt ≥ 6.5), and `cpack` makes the ZIP / DMG. zlib is built from source when the system has none (Windows).

## Architecture

Three layers with a strict dependency direction: `core` ← `link` ← `ui`.

- **`src/core/`**: pure C++, no Qt and no I/O. `VehicleState`, ArduPlane mode numbers and names, geo math including camera-ray-to-ground casting and the camera footprint, the mission builder, `health` (EKF/sensor/GPS/STATUSTEXT → plain-language advisories) and `OrbitTrim`.
- **`src/link/`**: plain C++, also Qt-free. It is compiled together with core into the `gcs_core` static library, which is what the tests link against. `MavlinkClient` owns a single worker thread that owns the `Transport` (`UdpTransport` or `SerialTransport`), parser, `MissionTransfer` state machine and `CommandSender` (retries and ACK handling). OS calls (sockets, termios) live only in the `*_transport.cpp` files. A transport that fails (port unplugged, autopilot rebooting) is reopened once a second. `reconfigure(Config)` swaps the link live (Settings → CONNECTION): it re-finds the vehicle and keeps its params and mission unless a different sysid answers. The worker loop waits at most 20 ms, so posted requests run within that (no wake fd). The UI thread only ever:
  - calls `snapshot()` to copy the latest `VehicleState`,
  - calls `pollEvents()` to drain `LinkEvent`s (command results, STATUSTEXTs, mission results),
  - calls request methods (`setMode`, `runSequence`, `uploadMission`, `guidedGoto`, `reconfigure`, ...), which post closures that run on the worker.

  Keep it this way: don't touch worker-owned members from other threads.
- **`src/payload/`**: payload ICDs (cameras etc.), also Qt-free and in `gcs_core`. Each `icds/<id>.json` (schema in `icds/README.md`) says how a payload's commands ride in COMMAND_LONG and how its reports ride in a carrier (V2_EXTENSION) with their own byte layout; `json.cpp` reads it, `icd.cpp` loads it, `icd_codec.cpp` decodes reports / encodes commands. `PayloadManager` (owned by `MavlinkClient`'s worker) matches messages by the ICD's sysid/compid *before* the vehicle filter, keeps the latest of each report with its rate, and runs payload commands through its own queue (ACK / retry, `ack: none`, answered-by-report, streams) so they never pre-empt the vehicle's `CommandSender`. The UI gets `payloadSnapshot()`, `sendPayloadCommand()`, `streamPayloadCommand()` and `LinkEvent::PayloadResult`. Optional `PayloadAdapter`s (`adapter.cpp` registry, `adapters/*.cpp`) turn reports into GCS terms (`PayloadView`: camera LOS / FOV / footprint, mode) and gestures into commands; a camera adapter's LOS replaces `cameraLos()` in `MainWindow::updateMotion` / `onCameraClick`, and a video tap (not guiding) asks it to track. `ui/payload_panel` is the generic panel built from the JSON (PAYLOAD chip next to HUD). The same JSON drives the Python simulators (`../nextvision_mavlink_sim`): `tests/payload_fixtures.inc` is generated from its packer (`tools/gen_cpp_fixtures.py`) — regenerate it after changing a layout.
- **`src/ui/`**: Qt widgets, touch-first. Map touch is handled in `MapView::event`: one finger goes through the same `pointer*` path as the mouse, and two fingers pinch. In PiP mode touch is ignored, so Qt synthesises the click that `ViewHost` swaps on. Other widgets rely on Qt's touch→mouse synthesis. Keep targets ≥ 44–48 px and don't put information behind hover only. `MainWindow` drives everything from a 16 ms `PreciseTimer` `frame()` tick that snapshots state, drains events and updates widgets. Rendering is mostly custom `paintEvent` code (map, camera HUD, effects overlay), not stock widgets. `ViewHost` handles the full-bleed main view and the swappable PiP. `ControlDock` holds the five action buttons and their lock/reason logic. Map tiles come from `TileCache`:
  - **Streets:** drawn by `VectorMap` from `offline/map.pmtiles`. That is OSM vector tiles (Protomaps schema), read with `core/pmtiles` + `core/mvt` + `core/gzip` and rendered on its own thread pool, never Qt's global one, which the raster engine waits on.
  - **Satellite:** the offline folder (`ui/offline_store`), then the browsing cache, then the network only when `map/online` is on (off by default).
  - **Filling gaps:** Esri's "no data" JPEG (`kEsriNoDataMd5`) is stored as a `{y}.none` marker, and `MapView` draws the nearest coarser tile enlarged, or the street map where there's no imagery at all.
  - **Downloads:** `OfflineDownloader` (country pack via `PmtilesExtract` range requests; full-detail areas drawn in `MapView::Mode::Area`) and `tools/fetch_offline.py` write the same layout, and every tile has one path, so overlapping areas share files.
  - **Ground height:** `ElevationCache` reads AWS terrarium tiles (tile maths in `core/tiles`). Video is only compiled when `GCS_HAVE_GSTREAMER` is defined. Everything internal is in metres; any altitude shown to the user goes through `ui/units` (`altText`, `altStepMeters`), which follows the m/ft setting. Only altitudes (and climb rate) follow it: distances and sizes are always metres. Problems are shown as `core::health` advisories in `AlertsPanel` (opened from SYSTEMS or the alert banner), not as raw flags. Battery time left is `core/endurance` (learned cruise/hover current, return-and-land cost from the worst plan point, margins, reserve). `MainWindow::updateEndurance` runs it every 2 s in flight and adds its cards to the advisories. The telemetry bar's TIME LEFT chip counts down in between. The bar is essentials only (LINK · BATTERY · TIME LEFT · FLIGHT · ETA · ALT · SPEED · SYSTEMS · ⚙); bar altitudes go through `core/display_round` (nearest 10, sticky), the commanded altitude is `MainWindow::commandedAltRel()` (what the GCS sent, not `nav_alt_error`), and AS / GS numbers live in the map's SPEED box.

`include/c_library_v2/` holds the vendored, generated MAVLink headers. They are included as SYSTEM, and link sources disable `-Wpedantic` and `-Waddress-of-packed-member`. Don't edit them.

## ArduPlane / SITL gotchas (verified against SITL)

- GUIDED takeoff must use `MAV_CMD_NAV_TAKEOFF` (22), not `MAV_CMD_NAV_VTOL_TAKEOFF` (84).
- Product rule: **the lift rotors are only for takeoff and landing.** Hold and Guide are GUIDED orbits via `DO_REPOSITION` (COMMAND_INT): `param2` flag CHANGE_MODE, `param3` radius, `param4` 0 = CW. Re-sending with the same centre changes the radius, altitude or direction live, which LOITER can't do (it only uses `WP_LOITER_RAD`). They are never QLOITER. A GUIDED takeoff ends in a rotor hover (`QPOS_POSITION2`), so `MainWindow::checkTakeoffHandoff` calls `hold()` at about the takeoff altitude. `Q_GUIDED_MODE` must be 0, or GUIDED targets end in a hover. The GCS reads it and alerts. Don't "solve" the rule by disarming in flight: that stops the pusher too.
- The mission layout (`core/mission.cpp`) is `HOME` → `NAV_VTOL_TAKEOFF` → route → optional `NAV_LOITER_TO_ALT` (the approach circle beside L, ±radius = CW/CCW, `param4` = 1 tangent exit) → `NAV_VTOL_LAND` (`param1` = 0). The landing is only reached through `MAV_CMD_DO_SET_MISSION_CURRENT`. The Land button first re-uploads the approach with the current `WIND`. Auto after an aborted landing sets the current item back to the loop.
  - ArduPlane only stays on the wing toward a VTOL_LAND beyond `transition_threshold = 1.5·v²/(2·Q_TRANS_DECEL)` (about 234 m at 25 m/s). Closer than that it goes straight to rotor position control. Its built-in spiral option (`param1` = 1) breaks out about one loiter radius from L, which is inside that threshold. In SITL that meant 79 s on the rotors. That's why the GCS builds its own circle and straight leg (`computeLandingApproach`).
  - `NAV_LOITER_TO_ALT` completes when the altitude is reached *and* the aircraft is heading toward the next item, so it leaves on the tangent.
  - The circle's `z` is the approach altitude. It must not be 0, because `Location::sanitize` reads a relative 0 as "current altitude".
  - The VTOL_LAND's `z` must be 0, meaning ground at home level. Without a rangefinder, ArduPlane uses the land item's altitude as the ground for its descent profile (`relative_ground_altitude` → `height_above_target`). With z = approach alt, it thinks it's already down and descends the whole way at `Q_LAND_FINAL_SPD` (0.5 m/s). In SITL that was 61 s instead of about 20 s.
  - The "VTOL land too short" arming check only fires when a `NAV_WAYPOINT` directly precedes the land item. The `LOITER_TO_ALT` in between avoids it.
  - The route depends on `MissionPlan::pattern`. Loop: WPs → `DO_JUMP`(→2, repeat −1). Back & forth: w1..wn, wn-1..w2 → `DO_JUMP`. One way: w1..wn-1 → `NAV_LOITER_UNLIM` at wn. A one-waypoint route is always `NAV_LOITER_UNLIM`. `extractPlan` reads the pattern back from the items (a mirrored route folds back to n points), so every rebuild (Land, wind refresh) keeps the item count. SITL-verified: back & forth flies 2,3,4,5,6,7,(jump)2. The final `LOITER_UNLIM` carries `MissionPlan::hold_radius` / `hold_ccw` as `param3` = ±radius (AP_Mission keeps |param3| in p1 and the sign as `loiter_ccw`; ArduPlane uses `WP_LOITER_RAD` when p1 ≤ 1, so "default CCW" is −1).
  - ArduPlane keeps flying the nav command it has in memory after a mission upload. So after a Sync while flying the plan in AUTO, `MissionUploaded` sends `SET_MISSION_CURRENT(rejoinSeq)` (the nearest point, keeping direction). A live end-hold edit (`sendEndHold`) re-loads the hold item itself.
- ArduPlane flies a GUIDED loiter bigger than `param3`: `AP_L1_Control::loiter_radius()` scales it by EAS2TAS² when `NAVL1_LIM_BANK` = 0 (+7 % at SITL's ~700 m AMSL), and L1 overshoots small circles (80 m flew as 91 m). `core::OrbitTrim` measures whole laps and commands `requested / ratio`, so send `trim_.commandRadius()`, not the requested radius.
- Q_ASSIST can spin the lift rotors in cruise, and speed assist sends no STATUSTEXT. The LIFT ROTORS indicator therefore reads `SERVO_OUTPUT_RAW` and maps outputs with `SERVOn_FUNCTION` 33–40.
- There is no QRTL button: Land is the one way down, and failsafes fly the same landing. Every mission the GCS uploads has a landing (L, or home when the plan has none) preceded by `DO_LAND_START` (189). With no plan it is HOME → `NAV_VTOL_TAKEOFF` → `DO_LAND_START` → `LOITER_TO_ALT` → `VTOL_LAND` at home (`buildLoopMission` with an empty route); Launch uploads it first when what is on board isn't ours (or its landing isn't at today's home). With `RTL_AUTOLAND` = 2 any RTL (long RC loss, GCS loss, low battery) jumps straight to it (`ModeRTL::navigate` → `jump_to_landing_sequence`). `Q_RTL_MODE` must be 0: with 2 (VTOL approach) `navigate()` returns before the autoland check, and 3 switches to QRTL on entry. `BATT_FS_LOW_ACT` 2 (Land) jumps to the sequence directly. A `DO_LAND_START` with `RTL_AUTOLAND` = 0 fails arming ("DO_LAND_START set and RTL_AUTOLAND disabled"). `MainWindow::refreshApproachForWind` re-uploads the approach when the wind turns ≥ 30°; a same-length re-upload mid-AUTO keeps the current leg.
- Safety at boot is `BRD_SAFETY_DEFLT` (1 = starts safe, reboot to apply; `AP_BoardConfig::board_init_safety`). SITL honours it.
- Gimbal: ArduPilot's `GIMBAL_DEVICE_ATTITUDE_STATUS` gives roll/pitch in the earth frame and yaw in the vehicle frame (flag). `core::cameraLos` turns that, or the fixed tilt setting, into an earth-frame camera attitude plus pan/tilt relative to the platform.
- ArduPlane reports `vtol_state` as FW while parked on the ground, so don't infer "hovering" from it alone.
- Resuming AUTO continues from the vehicle's *current* item. After a Hold during the AUTO VTOL climb that is still `NAV_VTOL_TAKEOFF`, and AUTO would hover and climb on the rotors again. `launchOrAuto` always sets the current item to `nearestLoopSeq()` first.
- After a VTOL landing the mission stays on the land item and AUTO won't arm ("In landing sequence", "missing takeoff waypoint"). Launch sends `SET_MISSION_CURRENT(1, reset)` before AUTO + arm.
- Safety switch: `SYS_STATUS` `MOTOR_OUTPUTS` is always present and *enabled* unless safety is engaged (`safetyState()`). Toggle with `MAV_CMD_DO_SET_SAFETY_SWITCH_STATE`; SITL implements it. Never while armed: it cuts every output, the pusher and servos included. There is no safety chip in the bar: while safety is ON the Launch slot is "Safety Off" (first hold → `makeSetSafety(false)`, second hold launches), and `MainWindow::autoSafetyOnLanded` turns it back ON on an armed → disarmed edge on the ground. After a flight `pf_->noteFlight()` asks for the turnaround preflight, whose lock comes before the safety step.
- RTL, QRTL and QLAND refuse arming ("mode not armable"), so after a failsafe landing the pre-arm bit fails although nothing is wrong. `reconcileLandedMode` turns that into an info card.
- Preflight (`core/preflight`, `ui/preflight_runner`, `ui/preflight_screen`): `MAV_CMD_DO_MOTOR_TEST` spins only the lift motors (test order A.. clockwise from front-right, `core/frame_layout` mirrors `AP_MotorsMatrix`); below ~15 % it doesn't pass spin-min. `DO_SET_SERVO` can't move assigned surfaces, so the surface test uses `MANUAL_CONTROL` in MANUAL (x = pitch, + is nose down). Calibrations ACK only when done: send once with a long timeout (`max_attempts`, `ack_timeout`). Disarm after a GCS-driven ground test with force (21196). Never one-tap `FENCE_ENABLE=1`: with no fence defined it fails pre-arm. ArduPilot after 4.6 has `ARMING_SKIPCHK` instead of `ARMING_CHECK`.
- Launch always takes off in GUIDED (`NAV_TAKEOFF`), even with a mission: an AUTO `VTOL_TAKEOFF` starts turning toward WP1 during the transition. At the takeoff altitude `startClimbOut` sends a straight `DO_REPOSITION` leg (300 m, into the wind, else straight ahead); `checkClimbOut` waits for wing-borne flight (VTOL state Cruise, airspeed, rotors not Active; 40 s timeout), then AUTO from WP1 (`firstRouteSeq`) or Hold. The mission's VTOL_TAKEOFF item stays for layout/failsafes.
- AGL comes from `DISTANCE_SENSOR` only when `rangefinderAgl` accepts it (down, < 1 s old, min < d < 0.95·max, quality ≠ 1, |roll|,|pitch| < 30°); otherwise the terrain map. A max-range reading means "nothing in range".
- `DO_CHANGE_SPEED` (airspeed) is accepted only within AIRSPEED_MIN..MAX; −2 = back to AIRSPEED_CRUISE. TECS raises its minimum by √(load factor) in turns (`AP_TECS.cpp`), so commanding AIRSPEED_MIN in a circle is safe. The GCS never writes the AIRSPEED_* params; `core/speed_mode` (`command()`) + `MainWindow::updateSpeedTarget` choose the airspeed in two layers: rules for every mode (Landing → CRUISE, Climbing > 15 m below the goal → CLIMB = LOITER speed, Descending > 15 m above it and steep (circling = `DescendingCircle`, or en route sinking > ½ `TECS_SINK_MAX`; along a long leg ArduPlane glides down a glide slope at ~0.5–1 m/s, which is level flight for speed) → DESCENT in ECO / NORMAL, and on a circle in FAST too (`core/descent_speed` `DescentTuner`: the slowest speed that sinks at `TECS_SINK_MAX` at idle throttle, stepped ±1 m/s per 8 s steady descent, saved as `speed/descent`; SITL: every speed sinks at the cap, MAX costs 16× the battery) and MAX in FAST en route, then a floor of wind + 5 m/s), and the speed mode for level flight (ECO: circling LOITER, en route CRUISE + ½ headwind toward the target, clamped LOITER..MAX; NORMAL: CRUISE; FAST: en route MAX, circling CRUISE). 3 s hysteresis per kind of target, landing at once, a continuous value re-sent only on a ≥ 1 m/s change, everything re-sent after a mode change. Plain CRUISE goes as −2.
- Waypoint holds are always set as a time (`UserWaypoint::hold_s`, operator decision). Default radius → `NAV_LOITER_TIME` (param1 s, param3 −1 = CCW); ArduPlane keeps no radius for LOITER_TIME (`verify_loiter_time`: always WP_LOITER_RAD). Own radius → `NAV_LOITER_TURNS` (param1 turns ≤ 255, param3 ±radius; AP_Mission stores ≤ 255 m exact, above /10 up to 2550; no spare param survives, so no time on board), with `hold_turns = holdTurns(hold_s, lapSeconds(r))` = ceil(time/lap)+1 kept by `MainWindow::syncHoldTurns` (and in `withLanding` before every upload). A radius equal to WP_LOITER_RAD is stored as 0. The GCS ends the hold itself (`MainWindow::updateWaypointHold`: timer from `onCircle`, then `SET_MISSION_CURRENT` to the next nav item, through a DO_JUMP to its target); the on-board item is only the link-loss backstop (both kinds otherwise circle on until heading for the next item). Uploaded hold times are remembered (`synced_holds_`, QSettings `plan/hold_times`) and put back into plans read from the vehicle (`fillHoldTimes`, `MapView::setPlanFixup`). The ETA is "arrived" (`NavTarget::arrived`, `onCircle`) once on a hold circle.
- PreArm STATUSTEXT cards (`AdvisoryBook`) live 35 s after their last repeat (ArduPilot repeats every 30 s), but go at once when the safety switch turns off (`prearm.txt.safety`) or the SYS_STATUS pre-arm bit is healthy (after 3 s, since a line can precede the bit).
- No keyboard shortcuts (operator decision): `MainWindow::eventFilter` swallows every key unless the `EntryPad` is open; the pad is the only keyboard consumer. The pad has one `QLineEdit` box per number (digit-only validators, a thick cursor via a `QProxyStyle`, hemispheres as toggles) in the Settings coordinate format; names (`openText`) get one free-text box and an on-screen letter keyboard; keypad buttons are `NoFocus` so the box keeps its cursor. LOITER speed = max(AIRSPEED_MIN, Q_ASSIST_SPEED + 2) ≤ cruise, or Q_ASSIST spins the rotors (SITL: assist 18 > min 13). Typed altitudes go through `core/altitude` (ASL/AGL/AFL → height above home, floor = ground at the point + 30 m, 20 m for the approach).
- Don't gate Launch on the prearm-healthy bit. It is evaluated for the *current* mode (e.g. "QRTL mode not armable") and doesn't apply to the mode Launch switches to.

## Plans

- **Only our mission counts.** `MainWindow::pullState` keeps `raw_mission_` and clears `s_.mission` unless `vehicleMissionOurs()` (`sameMission(raw, last_uploaded_)`, item 0 aside). `last_uploaded_` is set by every `MissionUploaded` and by adopting a download (armed / airborne at connect, or a long press on Plan); it isn't saved, so the GCS wakes with no plan. Everything downstream (map, Land, preflight, endurance) reads the masked `s_`. Event handlers run before the mask, on the raw snapshot.
- `active_name_` / `active_id_` name what is on the vehicle (set by a Sync); `editor_name_` / `editor_id_` / `editor_saved_` the editor's plan. "Edited" compares with `nearlySamePlan` (a plan read back from the vehicle is in 1e-7° and floats).
- Saved plans: `ui/plan_library` (QtCore only, tested by `test_plan_library`), one JSON file per plan in `<AppData>/plans/<uuid>.json`, name inside the file. `ui/plan_library_panel` is the PLANS panel (chrome widget, questions asked inside it). Names are typed with `EntryPad::openText` (on-screen keyboard).
- `hasFlyableMission` means "has a route": the landing-only mission is not one (Takeoff, not Launch; Resume Plan locked).

## Text size

Settings → DISPLAY → TEXT SIZE scales the UI by `theme::uiScale()` (1 / 1.25 / 1.5). Every size in UI code is a logical pixel at Small; scale it in exactly one of these ways, never two (or the font grows twice):

- Widgets that are all chrome (`TelemetryBar`, `ControlDock`, `SettingsScreen`, `AlertsPanel`, `PlanLibraryPanel`, `PreflightScreen`, `FxOverlay`) `p.scale(k, k)` and lay out in `logicalSize(size())`; taps go through `toLogical()`. Rects handed to other widgets (`FxOverlay::alertRect`) go back to physical pixels.
- Views keep their picture: `CameraView` scales only the HUD (`paintHudScaled`, `hudRect()`, `focal()` follows `hud_k_`); `MapView` scales its screen chrome (`paintOverlayChrome`, `chrome_k_`, taps divided by it) and draws markers / home / aircraft scaled around their map point. Lines, circles, trail, tiles and street labels don't scale. The PiP stays compact (k = 1).
- Stylesheet panels (`PlanStrip`, `OrbitPanel`, `WaypointPanel`, `SpeedPanel`, `EntryPad`) keep their sheet as a Small `kSheet` and `applyScale()` does `setStyleSheet(scaleCss(kSheet))` + `scaleWidgetTree(this)` (layout margins / spacing / spacers and min / max sizes, remembered at Small on first call). Build children with Small numbers; size from fonts after `ensurePolished()`, then invalidate + activate the layout before resizing (a stale hint overlaps the row).
- `MainWindow::applyTextSize` re-applies it live; the bar's height comes from `TelemetryBar::heightFor`, everything below the bar from `barBottom()`.

## Camera HUD

What the video overlay draws is a `core/hud_config` `hud::Config`: which elements are shown, the crosshair, line width, colour, which side boxes are folded, and the measuring brackets as angles. Presets are CLEAN / CUSTOM / FULL: `cfg.preset` is the lit one and `custom_show` / `custom_collapsed` hold the operator's CUSTOM mix, so change them only through `applyPreset` / `editShown` / `editCollapsed`. It is stored as `camera/hud` (`hud::encode` v2, millidegrees, no locale-dependent decimals); `decode` migrates v1 strings (no preset, a RULER REF bit at 11). What the rulers follow (LOS / BODY) is not in the config: it is `camera/hud_reference`, switched in `HudPanel` (`rulerRefChanged`); there is no chip on the video. `HudPanel` edits it live. `CameraView` draws from it, and reports box folds and bracket drags with `hudConfigChanged`. Every HUD pen goes through `lw()` and every HUD colour through `hudColor()`. Amber and red stay semantic. The measuring maths is `geo::pixelAngleDeg` / `anglePixels` / `sizeAtRange` on the picture's own width (`pictureRect()`, the letterboxed video), and the range is `LosTarget.slant`.

## Map colours

Green means the aircraft's current target and nothing else: the mission's current item only in AUTO (L / approach once landing), the GUIDED Hold / Fly To circle. The route dims (0.45) while airborne and not flying it. Home is white (`kText`), the vehicle route and an idle L / approach cyan, the plan being edited amber, cautions amber / red. A new map item that isn't the target shouldn't be green. (The camera footprint is the one exception, by choice.)

## UI motion

Telemetry arrives at 10–25 Hz. Don't draw the latest sample through a fast exponential tween: it arrives in about 60 ms and then sits still, which looks like a staircase. `MainWindow::frame` pulls every frame and calls `predictAttitude` / `predictPosition` (last sample + rate × age, capped), then views apply light smoothing on top.

## Paint budget

Everything repaints at 60 Hz in software, so each frame's full-window repaint must stay well under 16 ms on the target screen (1920×1200 here: ~6 ms map, ~8 ms camera). Measured costs at that size: 50 full-length AA grid lines ≈ 4.6 ms, a 6000-point trail ≈ 5 ms, smooth-scaled tiles ≈ 2.4 ms, a full-window radial gradient or pattern fill ≈ 1–2.5 ms, one full-window pixmap blit ≈ 0.3 ms. So:

- Anything that doesn't change every frame goes into a cached pixmap: `MapView` draws grid + tiles + the trail into a backdrop with a margin (`paintBackdrop`) and only shifts it; `CameraView` caches its vignette + scanlines.
- Don't keep transparent full-window widgets visible when idle: `FxOverlay` hides itself, because a visible one forces a full recomposite every frame.
- Qt 6's raster engine splits big fills over the global `QThreadPool`; `main.cpp` caps it at 2 threads (same frame time as 16, ~40 % less CPU). `GCS_PAINT_THREADS` overrides.
- Clip every line drawn from map coordinates to the view first (`drawClipped`, `drawLineClipped`, `circleVisible` in `map_view.cpp`). A leg to a far-off point (SITL restarted elsewhere keeps its old mission: 13 000 km) is millions of pixels long when zoomed in, and Qt rasterises every dash of it. That held the UI thread for ~3 s per frame.
- Measure with a driver that `repaint()`s widgets and times them, not by eye. `GCS_FPS=1` prints ticks, paints, stalls and telemetry rates live.

## Qt gotchas

- Qt's `emit` macro clashes with any method named `emit()`, so don't name methods that.
- `QTimer::singleShot` and default timers are coarse and can fire ~5% early. Use `Qt::PreciseTimer` where timing matters, including test and screenshot drivers.
